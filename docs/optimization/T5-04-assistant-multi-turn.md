# T5-04 · 检索助手的多轮对话支持（方案）

> 状态：**方案，未实现**。本文只做设计决策与代价分析，不包含实现代码。
> 前置：T5-01（kb-pack）、T5-03（role_intro）、T3-01（prompt 版本化）。

## 0. 一句话方案

**改写式（query rewrite）+ 无状态 API**：历史由调用方随请求传入，服务端不存会话；
有历史时先用一次小预算 LLM 调用把「追问」改写成自包含的独立问题，再走现有检索链路；
改写失败逐级降级，绝不阻塞主链路。

```
现状：  question ──────────────────────────→ 检索 → 门禁 → 作答
方案：  question + history[] ─→ ①改写 ─→ ②检索 → 门禁 → ③作答（带对话上下文）
```

## 1. 为什么必须做：单轮假设在追问场景直接失效

现在的 `_retrieve(question)` 拿到什么就检索什么，追问场景下会拿到一个**残缺的 query**：

| 上一轮 | 本轮输入 | 检索会发生什么 |
|---|---|---|
| 「EA 同步超时怎么处理？」 | 「xFlow 呢？」 | `xFlow 呢` 3 个字，bigram 覆盖率对谁都不高，大概率拒答或命中一堆同簇变体 |
| 「准入审批卡在提交了？」 | 「重试几次会好？」 | `重试` 与所有含重试字样的工单同分，排序不可控 |
| 任意 | 「它还有什么其他表现？」 | 「它」指代不明，检回来的东西和上一轮的根因毫无关系 |

这不是阈值调优能救的——**问题本身缺了主语**。缺的信息全在上一轮对话里，
所以解法必然是「让检索 query 继承对话上下文」，分叉只在于：在哪继承、由谁继承。

## 2. 关键决策一：历史放哪（服务端 vs 调用方）

**选调用方传入（请求体带 `history`），不做服务端会话存储。**

| | 调用方传入（选它） | 服务端 session（Redis/SQLite） |
|---|---|---|
| API 形态 | 无状态，扩容/重启零负担 | 要管 session 生命周期、过期、GC |
| 故障面 | 无新增 | session 丢失 = 对话断头，多一个降级分支 |
| 谁负责裁剪 | 调用方只管回放，服务端定上限并截断 | 同样要截断，但还多一层写入 |
| 与 trace 落库的关系 | 互不干扰 | 又多一张表 |

辅助链路的输出只给人看（T5 那条线），没有跨请求的机器消费场景，
为它引入服务端状态存储是过度设计。SSR 本身重启不丢的优势也不该被会话绑定破坏。

```python
class AssistRequest(BaseModel):
    question: str
    domain: str = "ssrm"
    history: list[dict] = []   # [{"role": "user"|"assistant", "content": str}]，按时间升序
```

服务端防御性截断（调用方不可信）：只保留**最近 `assist_history_max_turns=4` 轮**，
每条 `content` 截到 200 字符。上下文再长对改写没有增益，只有 token 成本。

## 3. 关键决策二：上下文在哪一层注入

三个候选位置，**选 A（检索前改写），B/C 作为作答阶段的辅助叠加**：

| 位置 | 做法 | 问题 |
|---|---|---|
| **A. 检索前改写 query** ✅ | LLM 把追问改写成自包含问题再检索 | 多一次 LLM 调用（见 §4 代价分析） |
| B. 检索时拼接原文 | `retrieve(question + history尾巴)` | 上一轮的词会污染覆盖率打分：上轮讲 EA，本轮问 xFlow，`EA` 的高频 bigram 会把 EA 簇顶进 top3——**答非所问且比分数看起来正常** |
| C. 作答时才给上下文 | 检索照旧、prompt 里带历史 | 治标不治本：检索就没检对，作答模型再聪明也是基于错误材料 |

B 是最容易「看起来做了」的方案，也是错得最隐蔽的方案——拼接后分数不会报错，
只会静默检错。改写唯一的问题就是贵，所以 §4 全部围绕「把这一次调用变便宜」。

## 4. 关键决策三：改写调用的成本控制

现状的 LLM 预算账（`.env`，T1-07 实测口径）：
`budget=15000`，`per_try=7000`，`retries=0`，两家 provider。
keyword+rerank 模式已有 rerank + answer 两次调用，**再加改写就是三次，账算不平**：

```
改写 7000 + 重排 7000 + 作答 7000 = 21000 > budget 15000   ❌
```

所以改写调用必须是小额切片，且带完整降级梯子：

```python
# 1. 小切片：budget.slice(assist_rewrite_timeout_ms=4000) 申请 4s，不是硬超时
# 2. 降级梯子（每级都可观测，span 记 rewrite_source）：
#    LLM 改写(4s) → 拼接最近两轮 user 原文（确定性，0 成本） → 原样 question
# 3. 改写输出必须校验：standalone 为空/超长 → 直接走下一级，不重试
```

降级后的行为不是随机变差，而是回到「单轮 + 拼接」的已知形态；
`rewrite_source` 进 span attrs，观测面板能直接看到各路径占比。

**改写 prompt（新增 `prompts/rag_rewrite.v1.md`，走 T3-01 版本化）要求输出 JSON：**

```json
{"standalone": "xFlow 回调丢失的工单怎么处理？", "topic_shift": false}
```

`topic_shift=true`（用户切换了话题）时**丢弃历史、用原问题**——这是防污染的保险丝：
上一轮的内容不允许泄进无关的新问题。

## 5. 作答阶段：轻量叠加

作答 prompt（`rag_answer`）新增一个可选段：`{recent_dialogue}`（改写时用过的最近 1~2 轮，
同样截断）。作用有限但值得做：模型可以把答案里的「它」替换成实体，减少下轮追问的歧义源头。
注意 **based_on 引用纪律不变**——引用只能指向本轮 `sources` 里的 id，不允许引用上一轮的案例
（上一轮材料没在本轮门禁里过阈值，引用了就是无门禁引用）。

## 6. 观测与评测（没有这两样，方案等于没做）

**观测**（复用现有 span/trace 体系，新增字段）：

| 字段 | 位置 | 用途 |
|---|---|---|
| `rewrite_source` | `rag.rewrite` span | llm / concat / raw，三条路径占比 |
| `topic_shift` | 同上 | 话题切换率，异常升高说明 prompt 有问题 |
| `rewrite_ms` / `provider` | 同上 | 4s 切片被掐的频率 |

**评测**（新增 `app/evaluation/rag_eval_multiturn.py`，20~30 个对话组）：

- 每组 = 2~3 轮，第 2/3 轮含指代/省略（「那 xFlow 呢」「它还有别的表现吗」）；
- 指标 1：**改写后检索的簇级 R@1**，对照「裸问题直检」（预期提升是主要收益证据）；
- 指标 2：**改写忠实度**——standalone 不得引入 history 里不存在的实体（防改写幻觉，
  人工标注或规则检查实体集⊆history∪question）；
- 指标 3：**topic_shift 判断准确率**（标注了该切换的组里切了多少）。

回归纪律：这组数据没建起来之前，改写上线只能算灰度，不能算「多轮检索准确率 X%」。

## 7. 明确不做的

| 不做 | 理由 |
|---|---|
| 服务端 session 存储 | §2，无状态优先 |
| 对话历史摘要压缩 | 4 轮上限内摘要是负收益：多一次调用，信息还没丢多少 |
| 嵌入相似度做 topic_shift 判断 | 20 组评测撑不起这个分类器，先用改写模型顺带输出 |
| 分类链路也加多轮 | `/handle` 是事件驱动，告警天然自带完整上下文，没有追问形态 |
| 有环澄清反问 | 与「两个 Agent 协作」的 C 方案同理：需要会话状态承载，投入产出比不成立 |

## 8. 实施顺序（每步可独立上线）

1. **API + 截断**（半天）：`history` 字段、防御性截断、config 三个新项
   （`assist_history_max_turns / assist_rewrite_enabled / assist_rewrite_timeout_ms`）。
   此步不改行为：history 传了也只透传。
2. **改写 span + prompt v1 + 降级梯子**（1 天）：keyword 模式先上（它的 rerank 已是
   「多一次调用」形态，边际成本感知最小）；hybrid 模式灰度。
3. **作答 prompt 加 recent_dialogue**（半天，走 prompt v3）。
4. **评测集 + 观测面板**（1 天）：20~30 组对话、multiturn eval、`rewrite_source` 进前端流水详情。

## 9. 面试一句话口径

> 多轮检索我设计的方案是改写式：API 保持无状态，history 由调用方传、服务端防御性截断到
> 4 轮；检索前用一次 4 秒切片的 LLM 调用把追问改写成自包含问题，改写失败降级到确定性拼接、
> 再降级到裸问题，每级都进 span 可观测；改写顺带输出 topic_shift 防止上一轮话题污染新问题。
> 不做服务端会话、不做历史摘要——辅助链路没有机器消费场景，那些是过度设计。
> 代价是多一次 LLM 调用，所以预算账要先算平：三次调用必须配切片，否则第二条 provider
> 永远轮不到——这是 T1-07 已经踩过的坑。
