# F14 观测扩展（每步成本与 run 视图）

迭代：I4 ｜ 依赖：F02 ｜ 代码：`oncall/observe.py` + `app/observability/` 小改

## 1. 目标

v1 能回答「这一次请求慢在哪」；v2 要能回答「**这个 run 的 12 步里，钱花在哪、卡在哪、哪一步是无用功**」。多了一个维度：步。

## 2. 复用与新增

| 能力 | v1 | v2 改动 |
|---|---|---|
| span 收集 | `tracing.py`，flat 列表 | 加 `parent` 与 `step_i` 两个字段（仍不做树） |
| 冷存 | `trace_store.py`（SQLite WAL） | 表加 `run_id`、`step_i` 两列 |
| 指标 | 滑动窗口 + 分钟桶（p50/p95/p99 15 分钟） | 新增 run 级指标（见 §3） |
| 导出 | OTLP/JSON 零依赖 | 不变（span 多两个 attribute） |

**为什么仍然不引 OTel SDK**：v1 的结论没变——单实例、一个人维护，SDK 的收益是「生态互操作」，成本是 collector + 上下文传播规范。协议出口已经有了，需要时换实现即可。

## 3. 新增指标（run 粒度）

| 指标 | 意义 | 异常信号 |
|---|---|---|
| `steps_per_run` | 步数分布（p50/p95） | p95 逼近 12 → 任务复杂度或卡住 |
| `tool_calls_per_run` | 调用次数 | 远大于步数 → 一步多工具（允许，但要看得见） |
| `compact_count` | 压缩次数 | 频繁压缩 → 单个工具返回太大 |
| `approval_wait_ms` | 等人时长 | 单独统计，**不算进 agent 延迟**（否则 p95 全是人的锅） |
| `tokens_per_run` | 成本主指标 | 结合 pass 看「每救回一单多少钱」 |
| `sensor_fail_rate` | 传感器拦截率 | 升高说明 prompt/工具描述退化 |

**`approval_wait_ms` 单列**这条值得强调：把人类思考时间算进 agent 延迟，是所有带审批系统的通病，最后没人看得懂大盘。

## 4. 面板（最小可用）

一页列表 + 一个详情：

- 列表：run_id / 事故 / 状态 / 步数 / token / 时长 / 是否挂起审批
- 详情：步骤时间轴（竖向），每步 `tool · args 摘要 · ms · token · ok`
- 点一步 → 跳 `/traces/{trace_id}`（v1 已有页面，直接复用）
- 挂起的 run 高亮 + 一键 `approve` 链接（CLI 命令文本，先不做按钮）

**不做**：新的可视化框架、实时 websocket。v1 的 React 页面加一个 tab 即可。

## 5. 与 F13 的关系

评测看的是**离线聚合**（30 条 × 3 组），观测看的是**在线单条**。两边共用同一套 span 字段，所以「评测里失败的那条」可以直接在面板里点开看它当时的每一步——这是排查「为什么这条没过」的最短路径。

## 6. 取舍

- **不做采样**：单机流量小，全量存；采样会在最需要的时候缺数据（v1 已记过这个结论）。
- **不做告警**：本项目没有值班链路，告警属于「接进公司体系」之后的事，写进限制即可。
- **不把 token 成本折算成钱**：模型价格变动快，折算会过期；只报 token，读者自己乘。

## 7. 验收

1. 一个 run 的 12 步在详情页完整可读，每步能跳到对应 trace
2. `approval_wait_ms` 不计入 run 总时长（断言：挂起 2h 的 run，`duration_ms` 不含那 2h）
3. 指标口径与 v1 一致：同一批请求，`p95` 在 run 视图与请求视图差异 ≤ 1%（口径一致性测试）
4. OTLP 导出：新增两个 attribute 后仍能被 collector 解析（v1 的 `otel.py` 有测试，扩展它）

## 8. 面试一句话

「加了 step 维度之后，观测要回答的问题变了：从『这次请求慢在哪』变成『这十二步里哪几步是白跑的』——所以我把审批等待单独拆出来，不然大盘上的延迟全是人在等人。」
