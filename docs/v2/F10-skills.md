# F10 Skill 运行时加载

迭代：I3 ｜ 依赖：F04 ｜ 代码：`oncall/skills_loader.py` ｜ 状态：**已实现（I6 补齐）**

## 0. 实现落点（先看这里）

| 环节 | 实现 | 位置 |
|---|---|---|
| 扫描 + 解析 | `SkillBook.reload()`：`skills/*/SKILL.md`，极简 frontmatter（name/description/triggers） | `oncall/skills_loader.py` |
| 常驻索引 | `index_text()`：每个 skill 一行，注入 `## 可用技能（匹配则先 load_skill 取正文）` | `oncall/context.py::build_messages` |
| 隐式命中 | `match(goal)`：trigger 原样出现在 goal 里才算；并列第一 = 歧义 → **不加载** | `oncall/loop.py` 首轮前 |

内置三个 skill：`incident-triage`（排障顺序）、`postmortem`（复盘六段）、
`kb-entry`（入库五步，复用 v1 文档）。加 skill = 加目录 + md，**不改代码**。

开关：`RunOptions.use_skills` / CLI `--no-skills` / 环境变量 `ONCALL_SKILLS=""`。

实测（真模型，glm-4-flash）：`"为什么 EA 同步超时影响 Dora 门户"` 命中
`incident-triage`，`[skill] {"matched": ["incident-triage"]}`；索引+正文合计
约 700 字符，未命中时只多约 200 字符（三条索引行）。

## 1. 目标

让「这类事该按什么流程做」变成**可插拔的知识包**：加一个 skill 不改代码，且平时不占上下文。

## 2. 与 v1 的关系

v1 已经有 `skills/kb-entry/SKILL.md`（五步入库流程），但**没有加载器**——它只是给人看的文档。v2 补的是运行时：扫描 → 索引 → 命中 → 注入。

## 3. 渐进披露（progressive disclosure）

| 阶段 | 上下文里有什么 | 成本 |
|---|---|---|
| 常驻 | 每 skill 一行：`name: incident-triage — 线上故障分级与取证顺序` | ~20 token/个 |
| 命中 | 正文（≤800 token） | 一次性 |
| 执行中 | 正文 + 脚本引用（`scripts/xxx.py` 路径，不贴代码） | 0 |

**为什么不让正文常驻**：5 个 skill × 800 token = 4k，等于为「可能用不到」付全价。渐进披露是 skill 相对「一段长 prompt」的唯一结构性优势。

## 4. 触发（两道，防误触发）

1. **显式**：模型可调 `load_skill(name)`——最可靠
2. **隐式**：描述匹配（关键词 + 现象特征）。

隐式触发的纪律：**description 写窄**。写成「检查知识库」会让任何提到知识库的对话都加载它；写成「新增或修改 KB 条目时使用」才准。v1 的 kb-entry 已经按这个原则写过，直接沿用。

## 5. 三个内置 skill

| skill | 触发 | 内容要点 |
|---|---|---|
| `incident-triage` | 「卡单/超时/报错/对不上」 | 取证顺序：工单 → 日志 → 变更 → 指标；每步该看什么字段 |
| `postmortem` | 结论已出、要写复盘 | 时间线、影响面、根因、动作、校验项 |
| `kb-entry` | 要把这次事故沉淀成 KB | 复用 v1 五步（判该不该入库 → 选簇 → 填内容 → 校验 → 验召回） |

`incident-triage` 是 v2 里**收益最直接**的一个：把「老值班同学的排障直觉」写成流程，模型第一次就能按对的顺序查。

## 6. 与 tool / sub-agent 的边界（避免又混起来）

- **tool**：一次动作（`read_logs`）
- **skill**：一种打法（先查什么、什么算证据、什么时候停）
- **sub-agent**：一个主体（会自己决定下一步）

skill 不执行任何东西，只改「模型看见什么」——它走 F04 的装配路径，不走 F03 的执行路径。

## 7. 取舍

- **不做 skill 市场/远程拉取**：供应链风险，且评测不可复现。
- **不做 skill 自动生成**：让模型自己写流程并复用，会把一次错误固化成长期习惯。
- **不做 skill 内嵌脚本自动执行**：脚本只能作为「人执行」的引用；自动执行等于绕过 F05 的副作用分级。

## 8. 验收

1. 新增一个 skill（只加目录 + md）→ 不改代码即可被命中（断言）
2. 未命中时上下文增量 ≤ 30 token/个（对比装配前后的 token 数）
3. 误触发：给「知识库怎么备份」这种问题，`kb-entry` 不应被加载（description 边界测试）
4. `incident-triage` 命中率：10 条事故里 ≥【待实测】条被正确触发

## 9. 通俗版：F10 到底解决什么问题（补）

一个具体对比例子说明它和「写死在 prompt 里」的差别：

**现状（没有 F10）**：值班排障的顺序知识——「先查工单 → 再查日志 →
再查变更 → 最后查指标，每步看什么字段」——这段经验要么写在
SYSTEM_PROMPT 里常驻，要么根本不在。写死的问题：

- 常驻付全价：这段 ~800 token，**每一轮每一次请求都带着**，哪怕今天
  的问题是问知识库怎么备份；
- 改流程要改代码：排障顺序更新（比如变更查询提到日志前面），要发版；
- 只能存一段：第二个领域（准入审批流程）也要类似的打法知识，prompt
  塞不下第二段。

**有 F10 之后**：这段经验变成 `skills/incident-triage/SKILL.md` 文件。
运行时的完整链路：

```
启动: 扫描 skills/*/SKILL.md → 索引(每条只记 name + 一行描述, ~20 token)
装配: build_messages 时把索引常驻注入 → 模型随时"知道有哪些 skill"
命中: 问题匹配上「卡单/超时/报错」→ 调 load_skill("incident-triage")
      → 正文 800 token 才进上下文(一次性)
```

三个直接收益对应 §1 的目标：

1. **加流程不改代码**：新 skill = 新建目录 + 一个 md，启动时自动被索引（验收 1 断言的就是这条）；
2. **平时不占上下文**：没命中时只花一行 token——这是它和「一段长 prompt」唯一但决定性的结构差别（§3 渐进披露）；
3. **流程知识可插拔**：第二个 domain pack 的准入审批打法，同样机制直接复用。

**最容易混的一点**（§6 已写，这里换说法）：skill 不会执行任何东西。
命中后它只是**改了模型看见的上下文**（多了一段流程指引），真正动手的
还是工具、决策的还是 loop。所以它走 F04 装配路径、不走 F03 执行路径，
也因此它**不需要**过四道关——它是知识，不是能力。

**与 F15 记忆的关系**：记忆（F15）是系统自己沉淀的历史事实（数据），
skill 是人写好的打法（知识）；记忆会变，skill 是显式维护的。两者都走
「命中才注入」的渐进披露，但来源、可信度、治理方式完全不同。

## 10. 怎么确认 agent 真的按 skill 走（不能不回答的问题）

先把结论说清楚：**无法确认，只能度量 + 兜底。** skill 注入的是上下文，
不是控制流——它没有任何强制力。任何声称「加载了 skill 所以模型会照做」的
说法，在架构上都站不住。

所以要把它拆成三个可验证的问题：

| 问题 | 手段 | 现状 |
|---|---|---|
| 加载了吗 | observer 的 `skill` 事件（`{"matched": ["incident-triage"]}`）+ `--verbose` 输出 | ✅ 已有，能确认注入发生 |
| 按流程走了吗 | 遵守率指标：命中 skill 的 case 上，统计 skill 声明的关键步骤（先 rag_search、再 query_incidents、顺序正确）出现率，与**未注入**的对照组比 | ✅ 已补（`bench/ab_subagents.py` 的「技能流程遵守率」段） |
| 不照做会怎样 | 门禁是否覆盖 skill 里的每条「必须」 | ✅ 见下表，这是真正的兜底 |

**关键设计原则：skill 里每一条「必须」，都必须有一条对应的机器门禁。**
否则那条「必须」只是建议，模型可以无视。`incident-triage` 的三条硬要求
与门禁的对应关系：

| skill 写的 | 对应的门禁 | 不照做的后果 |
|---|---|---|
| 第 2 步必须查历史工单（第二来源） | S2 双源门禁（`sensors.check_finish`） | finish 被退回，进 F17 修正轮 |
| `enough=false` 必须 unknown + 转人工 | S1 引用校验 + S3 类名合法性 | 类名不合法直接退回；unknown 才算合法拒答 |
| 涉重启/删除/清空 → 停，交人工 | F05 策略门禁（WRITE 需审批） | 工具被拦成 pending_approval |

只有一条没有强制：**「先 KB 再历史」的顺序**。这是刻意的——顺序错了
不影响结论正确性（两个来源都有就过门禁），而强制顺序会把 skill 变成
pipeline，失去它作为「打法」的意义。

**所以 F10 的价值定位要诚实**：它影响的是**效率**（少走弯路），不是**正确性**
（正确性由门禁保证）。实测数据（30 条多跳、真模型，见 `bench/report-ab-subagents.md`）：

| 臂 | pass@1 | 步数 | token | 调过历史工单（第二来源） |
|---|---|---|---|---|
| 注入 skill | 20% | 1.8 | 194k | 3/3 |
| 不注入 | 20% | 1.6 | 169k | **0/3** |

行为确实变了（3/3 vs 0/3），但**结果没变**，还多花了 15% token。一个合理的
解释是：F17 的确定性补齐会在模型不查 history 时替它查——**skill 教会模型
自己做，harness 在它不做时替它做，两条路等价**，所以 pass@1 拉不开差距。
样本只有 3 条命中，不足以下强结论；但它已经说明一件事：**skill 的收益
要靠「harness 兜不了底」的任务来体现**（多轮、跨域、需要判断先后的场景），
在单轮排障上它只是把同一件事换个地方做。

## 11. 面试一句话

「skill 的价值不是『存了一段 prompt』，而是『平时只花一行 token，命中才付全价』——这是它跟长 prompt 的唯一结构差别，也是它必须窄触发的原因。」
