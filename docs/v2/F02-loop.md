# F02 Agent loop（终止 / 预算 / 无进展检测）

迭代：I1 ｜ 依赖：F01 F03 ｜ 代码：`oncall/loop.py`

## 1. 目标

一个**能停下来、停得有理、停得住**的循环。三件事必须显式设计，缺一个就会在生产上出事故：终止条件、预算、无进展检测。

## 2. 循环体

```
state := {goal, facts[], hypotheses[], excluded[], steps[], usage}
while True:
    ctx  = assemble(state)              # F04
    out  = llm.chat_json(ctx)           # 复用 v1 的 JSON mode + 容灾
    # out: {action: "tool"|"finish"|"ask_human", tool?, args?, thought?, confidence?}
    if out.action == "finish":  → 过 F07 传感器 → 结束
    if out.action == "ask_human": → 结束(needs_human)
    result = policy.execute(out.tool, out.args)   # F05：鉴权/审批
    state.facts = update(state.facts, result)     # 结构化事实，不是原文堆叠
    if 触发终止条件: break
```

**关键：状态里存的是结构化事实，不是消息列表的机械增长。** 每轮只把「新确认的事实」追加进去，原文留在 trace 里。这一步决定了 F04 的压缩能不能做。

## 3. 终止的五个条件（互相独立，先到先停）

| 条件 | 阈值 | 触发后行为 | 管的是什么 |
|---|---|---|---|
| 模型主动 finish | — | 过传感器；不过则回 loop 再补一步（最多 2 次） | 正常结束 |
| 步数上限 | 12 | `status=budget_exhausted`，吐当前最佳结论 + 缺失项 | 任务规模 |
| 墙钟预算 | 90s | 同上，且不再发起 LLM 调用（`MIN_TRY_MS` 逻辑） | **用户等多久** |
| token 预算 | 100K（prompt+completion 累计） | 同上 | **这次 run 花多少钱** |
| 无进展 | 连续 2 次无新增事实 | `status=needs_human`，附「卡在哪」 | 模型行为 |

时间与 token 是两种不同的失控：便宜的模型跑很多步、和贵的模型三步烧掉一个大 prompt，一个上限兜不住两者。token 只能在**每次调用后**记账检查——API 不会提前告诉你这次花多少，事后截断是唯一能做的。正常排障 12 步 × 每步 4~6K 约 30~50K token，100K 是兜底不是常态（到顶说明在打转，步数/无进展会先拦）。

**为什么是 12 步**：单跳排障通常 3~5 步（查工单 → 查日志 → 查变更 → 结论）；多跳 7~9 步；超过 12 步基本是在打转。这个数会在 I1 结束后用实测步数分布校准，不靠拍脑袋。

### 3.1 上限触发后「结果依然不理想」的三层处理

1. **不丢已查到的东西**：返回的 `Outcome` 带全部 `facts`（带 ref）、全部 `steps`（哪步被拒/截断）、`reason` 写明哪条额度先耗尽。查到 80% 的证据被扔掉和查了 0 步是不同的失败。
2. **出口区分**：时间/token/步数耗尽 → exit 3（`budget_exhausted`），业务层可基于 facts 出「部分结论 + 缺什么」；打转 → exit 2 直接转人工。
3. **resume（I2，F06）**：步数/token 上限触发的 run 落库后可 `oncall resume <run_id>` 续跑——已查过的事实不重查，这正是事实必须带 ref 持久化的原因。

### 3.2 生产上的耗时优化（90s 是 run 级预算，不是单请求超时）

90s 是**整个 run 的墙钟**；单次 LLM 调用的超时是 `min(per_try, 剩余预算)`（`budget.slice` 直接传给 LLM 客户端）。用户体感优化三板斧：

1. **流式输出**：final answer 阶段边生成边吐，用户从「等 60s 出全文」变成「10s 开始看到字」——体感延迟降一个量级，总时长不变
2. **每步进度事件**：observer 回调就是为此留的钩子，CLI `--verbose` / Web SSE 把「正在查工单库…」推给前端，等待变成可见的过程
3. **交互面降预算、批处理升预算**：值班同学在线问 → `--budget-ms 45000`；nightly 批量评测/定时巡检 → 300s 都行。预算是按入口配置的，不是全局常数

## 4. 无进展检测（最容易被忽略的一条）

两个信号，任一命中即计数 +1：

1. **同工具同参数重复调用**：指纹 `sha1(tool + sorted(args))` 进集合，命中说明模型在原地转
2. **observation 无新增事实**：把工具结果归一化成事实集（字段 + 值），与 `state.facts` 求差集为空

计数达 2 → 直接退出，**不重试**。理由：重复调用不会因为再试一次就变成有信息，继续跑只是烧钱。

反例（真实会发生的）：模型查到「回调地址是旧的」，但它不认为这是因，于是又查一遍日志、又查一遍工单——这就是典型的「有证据、无进展」。此时正确行为是带着已有的两个事实转人工，而不是再跑 8 步。

## 5. 与 v1 的关系：把分类器变成确定性工具

**根因分类不做 agent 化**（见 README §2）。做法是把 v1 的 `classify` 包成一个工具 `classify_incident(text)`：

- 输入：现象描述（必要时带已收集的事实）
- 输出：`{root_cause_class, confidence, evidence_mode}`
- 特性：**确定性、无循环、几百毫秒**

模型可以选择调它，也可以不调（简单事故直接给结论）。这样做的三个好处：

1. 分类的评测集与门禁逻辑全部复用，不重写
2. 模型不用「重新推理一遍分类体系」，少一类幻觉
3. 面试可讲：**用确定性组件约束 agent**，而不是让 agent 重做一遍已有能力

## 6. 取舍

- **不做 plan-then-execute**：多跳排障里计划 30 秒就失效（查到的东西推翻假设）。用「事实 + 假设 + 已排除」三列表代替计划，允许随时改方向。
- **不做 self-reflection 单独一轮**：反思塞进下一轮 prompt（「你已排除 X，因为 Y」），省一次调用。
- **不做 while True + 最大步数兜底**：那是把所有失败都归因成「步数用完」，无法区分「打转」和「任务真的复杂」。

## 7. 验收

1. 10 条单跳事故：pass@1 ≥【待实测】，平均步数 ≤ 6
2. 人为构造「重复调用同一工具」的桩 LLM：必须在第 3 步触发 abort，且 `status=needs_human`
3. 预算测试：注入 `budget_ms=2000` 的桩，必须在预算耗尽时停止发起 LLM 调用；注入 `max_tokens` + 逐次上报 `_usage` 的桩，跨过上限的那次调用允许完成、之后必须停
4. 单测覆盖五个终止条件各一例（桩 LLM，零网络）

## 7bis. I1 首次真跑的三条发现（真实调试记录，比设计更有面试价值）

第一次用真模型（glm-4-flash）跑通 CLI 时，连着暴露了三个问题，修法都在 scaffold/治理层：

1. **模型不会主动 finish**：拿到 `kb_stats` 的答案后又连查两次同样的东西，被无进展检测拦下（这条检测第一次真跑就立功了）。修法在 prompt：加「已确认事实足以回答任务时，必须直接输出 finish」。——**这是 scaffold 问题，不是 harness 问题**；harness 的职责是兜底，不是替模型思考。
2. **模型漏掉 `confidence` 字段**：缺省被当成 0 → 永远低于 0.7 → 任何工具都执行不了，模型开始说「我不知道」。修法：区分「自报了低置信」与「没自报」——前者是判断，后者是格式问题。缺省时只读放行、有副作用照旧挂起，风险由副作用等级兜，不靠一个缺失的字段。
3. **S2 一刀切要求双源**把纯查询拦成了「需要编证据」：改成按「是否断言根因」条件化（见 F07）。

三条共同指向一个结论：**loop 的失败大多不是「模型太笨」，而是「契约没说清 + 门禁一刀切」**。排障时先分 scaffold / harness 两侧，能省一半时间（与 2.6 节的分法一致）。

## 8. 面试一句话

「loop 不难写，难的是知道什么时候该停——我给了五个独立终止条件，其中无进展检测是最容易被忽略的那个：模型重复查同一样东西时，再跑十步也不会变好。时间和 token 也是分开管的：一个管用户等多久，一个管这次花多少钱。」
