# F11 Sub-agent 并行取证

迭代：I3 ｜ 依赖：F02 F07 ｜ 代码：`oncall/subagent.py` ｜ 状态：**已实现（I6 补齐）**

## 0. 实现落点与「什么时候发生作用」（先看这里）

**默认两路线（ssrm）**：`kb`（rag_search，找类名+处置动作）、`topology`
（system_topology，找链路上哪一环最可疑）。**history 刻意不并行**——它必须先
有类名才能查，天然依赖 kb 结论，硬放进来等于让子 agent 猜类名；那条线由
F17 的确定性补齐负责。真实 SRE 部署里把 logs/metrics/changes 加进
`EVIDENCE_LINES` 即可，机制不变（**线是数据，不是代码**）。

**触发条件（`should_spawn`）——三条同时成立才 spawn：**

| 条件 | 原因 |
|---|---|
| 至少两路可用（工具都在注册表、且都是 `READ`） | 一路并行没有意义，串行调工具更便宜 |
| `mode=auto` 时 goal 含多源线索：`为什么/影响/上下游/链路/对比/分别/同时/影响面/根因…` | 这些词意味着结论要串联 ≥2 个信息源 |
| 首轮且 facts 为空（resume 不再 spawn） | 事实已在库里，再跑一遍就是重复烧钱 |

开关：`RunOptions.subagents = auto|off|force`、CLI `--subagents`、bench
`--subagents`（**默认 off**，打开它是一次显式消融，不让历史数字漂移）。

**每路的运行规格**：只读工具子集（写工具从机制上不给）+ 独立上下文 +
独立 facts + ≤3 步 + 20s 超时；回传结构化 `Finding`（summary/evidence/
class_guess/unresolved），合并成普通事实（field 保持 kb/topology 原口径），
主 loop 的门禁口径**零改动**。

**冲突纪律**：两路 `class_guess` 不同 → 落一条 `field=conflict` 的事实，
并禁止模型断言根因（真模型试过：门禁退回 + 转人工，不是投票选一个）。

**真模型实测（glm-4-flash，2 路）暴露并修掉两件事**：

1. 子 agent 会「再查一次确认」把 3 步烧完还不 finish → 同一工具第二次调用直接
   拦下（`重复调用同一工具`）+ 最后一步强制 finish；
2. 会把工具清单里的字段定义当 args 传（`{"query": {"type":"string"}}`）→
   sub-agent prompt 明确「args 只填值」，并给一行例子。

实测结果：两路都能产出 summary（`2 路有结论`），topology 路质量的稳定性明显
好于 kb 路；弱模型下 kb 路常给「已取到，但不足以判断」——这是模型能力问题，
但**结构上不会污染主上下文**，也不影响主 loop 继续取证（这是隔离的价值）。

## 1. 目标

把「日志 / 指标 / 变更」三路互不依赖的取证并行化，**同时把噪声隔离在各自的上下文里**，主 agent 只接收结论。

## 2. 两种动机（都要能说清，否则会被问「是不是多此一举」）

| 动机 | 说明 | 什么时候成立 |
|---|---|---|
| **上下文隔离** | 一次日志取证可能 3k token 噪声，主 agent 只需要「有没有 404」这一句 | 数据源噪声大 |
| **并行降延迟** | 三路串行 9s → 并行 4s | 三路互不依赖 |

**不成立的时候**：第二路依赖第一路的结论（「先看日志才知道该查哪个指标」）。此时串行更便宜，也不会有结论冲突。

## 3. 设计

```
main.run()
  ├─ spawn(logs)     ─┐  各自：只读工具子集 + 独立上下文 + 步数上限 4
  ├─ spawn(metrics)  ─┼→ Finding{结论, 证据[], 置信度, 未解问题}
  └─ spawn(changes)  ─┘
  合并 → 冲突检测 → 主 loop 继续
```

每个子 agent 的约束：
- **只给只读工具**（F03 的 `READ`），从机制上保证子 agent 永远不能产生副作用
- 步数上限 4（子任务比主任务窄，给 12 步没有意义）
- **必须回传结构化 Finding**，不接受自由文本（自由文本合并时会二次失真）

## 4. 一个真实的坑：span 会丢

v1 的 `tracing.py` 用 `contextvar` 收集 span，注释里已经写明：

> `asyncio.gather` 起的并发子任务里 `set` 不会回传到父上下文，那些 span 会丢

所以 F11 不能直接 `gather` 了事，必须：**在子任务内新开一个 span 收集器 → 结束后回传 list → 主任务合并并标 `parent=subagent:<name>`**。这条不是理论问题，是 v1 里已经踩过的。

## 5. 冲突处理（多 agent 最容易被问的地方）

| 情况 | 处理 |
|---|---|
| 三路结论一致 | 直接采信，证据合并（字段去重后计数） |
| 两路一致、一路沉默 | 采信多数，沉默那路记「未覆盖」 |
| 两路**互相矛盾** | **不投票**：把矛盾作为「待人工」的显式理由输出（矛盾本身就是信息） |
| 子 agent 超时 | 主 agent 用剩余信息继续；不重试（重试会把延迟拉回串行水平） |

**为什么矛盾不投票**：三路里两路一致不代表对——可能两路看的是同一个错误数据源。投票会把「数据源问题」变成「结论」，这是最危险的一种自动化。

## 6. 取舍

- **不做子 agent 嵌套**：子 agent 不能再派子 agent，否则预算与 trace 都会失控。
- **不做子 agent 写入**：见 §3，机制上禁掉。
- **不默认并行**：先判「是否 ≥2 路且互不依赖」，满足才并行；单路直接顺序调工具。

## 7. 验收

1. 延迟：三路各 3s 的桩 → 总耗时 ≈ 3.2s（允许 20% 浮动）
2. 上下文隔离：主 agent 装配后的 token 数 ≤ 串行版本的【待实测】%
3. 冲突用例：构造 logs 说 404、metrics 说 200 → 结论必须是 `needs_human` 且列出矛盾
4. span 完整性：一个 run 的 span 里，三个子 agent 的 span 都在，且 parent 正确（这条最容易漏）
5. 子 agent 试图调写工具 → 被拒（断言 policy 调用次数为 0）

## 8. 常见误解：日志/指标/变更明明是工具，为什么还要 agent？

先承认前提：**是的，`read_logs` / `query_metrics` / `list_changes` 每一个
都是普通工具**（F03 注册、四道关保护），这一点没有任何争议。

问题不是「调不调工具」，而是**「每一路要调几次、谁来决定下一步」**：

- 一次日志取证往往不是一次调用：先按时间窗过滤 → 发现 404 → 查上游
  服务 → 查配置版本——这一串里每一步的**查询参数取决于上一步的结果**
  （「看到 404 才知道该去查哪个服务」）；
- **工具只能执行单次动作**，把「结果→决定下一次调用」串起来的循环体，
  就是一个 agent loop。这是定义问题，不是架构偏好。

三种实现形态的对比：

| 形态 | 做法 | 问题 |
|---|---|---|
| ① 主 loop 串行调 | 三路全在主上下文里调工具 | 日志 3k token 噪声全进主上下文；三路串行慢 |
| ② 固定 pipeline | 每路写死调用序列 | 「下一步查什么」依赖中间结果，写死就覆盖不了 |
| ③ **只读子 agent** | 每路一个 ≤4 步的小 loop 自主决定调用序列 | 噪声关在子上下文，主 loop 只收 Finding |

什么时候**真的只需要工具**：当一路取证可以「一次调用出结论」（如
`kb_stats` 看仪表盘）——它就是主 loop 里的普通工具调用，spawn 子
agent 反而是浪费。所以 §6 写了「不默认并行」：**按每条路的复杂度决定
用工具还是子 agent，不是看见三个数据源就上多 agent**。

一句话：**工具回答「这一步怎么查」，子 agent 回答「这一路怎么查」；
取证路上存在「看结果再定下一步」，就需要一个 loop 来承载这个决策，
只不过把它关进只读+限步的小盒子里。**

## 9. 怎么确认它真的起作用（以及负影响长什么样）

「我觉得并行会更快」不是理由。要证明它有用，必须回答三个独立的问题，
任何一个答不上来，这个能力就应该默认关掉：

### 9.1 触发了吗（触发率）

`should_spawn` 的三个条件里，前两个是**前置条件**不是判断：

| 条件 | 实际情况 |
|---|---|
| ≥2 路只读线路可用 | 默认恒真——`rag_search` + `system_topology` 都在注册表里且都是 READ（实测 `available_lines()` 返回 `['kb','topology']`） |
| 首轮且 facts 为空 | 调用点保证：`not initial_facts` 才进（resume 不重跑） |
| goal 含多源线索词 | **唯一的真判断**，纯字符串匹配 |

实测这个唯一判断的门槛有多高：**200 条评测集里 `auto` 只放行 1 条（0.5%）**。
原因不是判据写错，而是真实 goal 几乎不写「为什么/影响面/链路」——
它们是现象描述（「EA 主数据同步超时，注册卡单」）。

这个数字说明 F11 在当前形态下是**一个几乎不会被触发的旁路**。
两个可选修法：

1. 换判据：改成「结构性信号」——goal 命中的根因簇 ≥2（复用 F18 路由探针的
   类别分布），或者路由器判为多跳；不要看用户怎么措辞；
2. 换时机：从「首轮预猜」改成「缺口驱动」——等门禁退回、且缺口是
   topology/history 时再并行补（此时已知类名，history 也能进并行组）。
   **这个改法更符合 F17 的思路：不做无根据的预判，只对确定的缺口动手。**

### 9.2 取到了吗（产出率）

`Finding.summary` 非空且 `error` 为空才算这一路有结论。日志与 `--verbose`
里能看到「并行取证：2 路（N 路有结论）」。真模型实测的坑已经修过两个
（反复调同一工具、把 schema 当 args），但 kb 路在弱模型上仍常给
「已取到但不足以判断」——这不算失败，噪声被隔离在子上下文里，
主 loop 继续取证。

### 9.3 有没有用（净效应，必须消融）

只看「子 agent 跑起来了」没有意义，要看**只差这一个变量**时结果变不变。
`bench/ab_subagents.py` 的三臂：

- `base`：skills 开 + 并行关（现状）
- `sub`：skills 开 + 并行 `force`（只多一件事）
- `noskill`：skills 关 + 并行关（只少一件事）

**一定要先修判分口径再跑**，否则会得到一个假的负结果：子 agent 调的工具
记在 `Finding.steps` 里，而 judge 的 `called_tools` 只读主 loop 的 steps——
**并行取证越有用，主 loop 越省步骤，判分反而越差**。这是评测口径伪影，
不是能力差异。修法：`run_harness_case` 回传 `sub_called_tools`，
judge 用 `called | sub_called` 判关键步骤。

实测这两版的差别（同一批 30 条、同一模型）：

| judge 口径 | base | sub | 结论 |
|---|---|---|---|
| 只认主 loop 的工具 | 20% | **13%** | 「并行取证是负影响」——错的 |
| 合并子 agent 的工具 | 20% | **47%** | +27pp，真有效 |

这是本次最值得记住的一条：**评测口径的 bug，会把一个有效能力判成有害。**

修完口径的完整结果（`bench/report-ab-subagents.md`）：

| 臂 | pass@1 | 平均步数 | token | p95 |
|---|---|---|---|---|
| base（并行关） | 20% | 1.8 | 194k | 31.0s |
| sub（并行 force） | **47%** | 2.1 | 332k | 41.4s |
| noskill（无技能） | 20% | 1.6 | 169k | 32.2s |

逐条看是 12 条转正、3 条转负——**有得有失，不是全赢**。代价也很实在：
token +71%、p95 +34%（两路各 2~3 轮调用换来的）。

### 9.4 负影响的五种形态（都要盯）

| 形态 | 机理 | 观测手段 |
|---|---|---|
| token / 延迟翻倍 | 两路各 2~3 轮 LLM 调用 | `tokens_total`、`p95_ms`（token 记账修复后才可信） |
| 伪证据进主上下文 | 子 agent 的 quote 是二手转述，可能不是原文 | S1 引用校验会拦 → 表现为「被门禁退回」而不是错误结论 |
| 冲突导致过度转人工 | 两路 `class_guess` 不同 → 落 `conflict` 事实 → 模型不敢断言 | `needs_human` 占比上升、`status=needs_human` 里 reason 含「冲突」 |
| 首轮预猜打偏 | goal 措辞触发但实际不需要拓扑 | 子 agent 路数 >0 但 `unresolved` 非空 |
| 与 repair 轮抢预算 | 首轮烧掉 2~3 次调用，`budget_ms` 剩余变少 | `budget_exhausted` 占比 |

### 9.5 判定标准（什么情况下该关掉）

- 净效应（sub vs base）在样本量内不显著 → 保留 `auto` 但**不要扩大触发面**；
- 任一负影响形态明显恶化（p95 上升 >30%、转人工率上升 >10pp）→ 默认关；
- 只有当「缺口驱动」改造完成后，才值得讨论把它接进主路径。

> 数据见 `bench/report-ab-subagents.md`。样本 30 条时单条 = 3.3pp，
> 两三条的差异在噪声内——报告里如实标注，不据此下强结论。

## 10. 面试一句话

「sub-agent 不是为了让架构图好看，是为了两件具体的事：把噪声关在别人的窗口里、把三路串行变并行。所以它有两个硬约束——只读、必须回传结构化结论；做不到这两点，它只会让成本和不确定性都翻倍。」
