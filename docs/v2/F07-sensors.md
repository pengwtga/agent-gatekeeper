# F07 验收传感器（证据 / schema / dry-run / reviewer）

迭代：I2 ｜ 依赖：F03 ｜ 代码：`oncall/sensors.py`

## 1. 目标

在 agent 说「我完成了」之后、把结论交给人之前，**自动判断它是不是真的完成了**。这是 harness 里最像「工程」而不是「提示词」的部分。

## 2. 传感器分两类（Böckeler 的二分法）

| 类型 | 特点 | 本项目里是谁 |
|---|---|---|
| **计算型**（确定性、便宜、可重复） | 每次都同答案，毫秒级 | 证据字段数、schema 校验、命令白名单、`--dry-run` |
| **推断型**（再调一次模型、贵、会错） | 能抓语义问题 | reviewer：结论是否被证据支持、是否有更简解释 |

**分工原则**：能用计算型判的绝不用推断型。推断型只在「快结束时跑一次」，且用便宜模型。

## 3. 五道传感器

| # | 传感器 | 类型 | 判据 | 失败后 |
|---|---|---|---|---|
| S1 | 结论非空且可执行 | 计算 | `conclusion` 长度 > 10 且不含「可能/大概」这类模糊词打头 | 回 loop 补一步 |
| S2 | 证据足够 | 计算 | `evidence` 中 **distinct field ≥ 2**（复用 v1 `evidence_refs_fields` 口径）；**仅当结论断言了根因**（`root_cause_class != "unknown"`）。纯查询只要求 1 个来源 | 回 loop 补一步 |
| S3 | 证据可追溯 | 计算 | 每条 `ref` 能在 trace/配置/工单里查到 | 剔除无效证据，重判 S2 |
| S4 | 动作安全 | 计算 | 若结论含写动作：必须已过 F05；shell 类必须 `--dry-run` 通过 | 降级为「建议 + 待人工」 |
| S5 | 结论被证据支持 | 推断 | reviewer 只做一件事：给出反例或「支持」 | 回 loop 一次，仍不过 → needs_human |

**S2 为什么要求「不同字段」而不是「条数」**：v1 踩过——同一句日志切两段就能凑够 2 条，形成假满分。字段去重逼着 agent 从**两个独立来源**取证（日志 + 配置、指标 + 变更）。

**S2 为什么是条件化的（I1 实测教训）**：第一次真跑就把「知识库有多少条」拦了——模型给了正确答案、唯一权威来源就是 `kb_stats`，硬凑第二个字段只会逼它编证据。所以改成**按结论类型区分**：断言了根因（`root_cause_class != "unknown"`）才要求跨源印证；纯查询 1 个来源即可。传感器的松紧要跟着「断言的风险」走，不然它会变成「为了过检查而编证据」的激励。

## 4. reviewer 的 prompt 契约（越小越稳）

```
输入：结论一句话 + 证据列表（field/ref/quote）
任务：只输出 {"verdict": "support"|"contradict"|"insufficient", "reason": "≤30字"}
禁止：评价结论是否「合理」，只判断「证据是否足以推出结论」
```

三条纪律：
1. **不给它工具**——reviewer 一旦能自己查，就变成了第二个 agent，成本和不确定性都翻倍
2. **不评「对不对」只评「够不够」**——对错需要领域知识，够不够只需要逻辑
3. **失败不阻塞**：reviewer 超时/报错 → 视为 `insufficient`，转人工，不重试

## 5. 重试预算（防止「验收」变成死循环）

- 每个传感器失败后最多触发 **2 次**回 loop
- 总计最多 2 次（不是每个传感器各 2 次）
- 用完仍不过 → `status=needs_human`，结论字段保留但标记 `unverified`

## 6. 与 v1 的关系

v1 的证据门禁是**生成后的事后校验**（分类器输出后数 refs）。v2 把它前移成**完成前的传感器**，并且：
- 判据代码复用（同一函数、同一单测）
- 但触发时机不同：v1 是「输出即终态」，v2 是「不过就再跑一步」

这是「门禁」到「传感器」的演进：**门禁只能拒绝，传感器能让它改。**

## 7. 取舍

- **不做全自动修复**（比如自动补一条证据）：补出来的证据就是编的。
- **不做多 reviewer 投票**：成本三倍，收益不确定；单 reviewer + 人工抽检更实在。
- **不做「结论置信度自评」当传感器**：模型自报的置信度不校准（v1 已验证），只能当裁剪信号，不能当验收标准。

## 8. 验收

1. 构造「结论漂亮但证据只有 1 个字段」：S2 必须拦，且回 loop 后能补齐（桩数据）
2. 构造「同一句日志切两段」：S2 必须拦（字段去重生效）
3. 构造「结论与证据矛盾」（日志说 200，结论说 404）：S5 必须 `contradict`
4. reviewer 超时：不抛异常，降级 `insufficient`，总耗时 ≤ 预算
5. 传感器全程不调用写工具（断言）

## 9. 面试一句话

「验收分两半：能算的用代码算（证据字段数、schema、dry-run），算不了的才让模型判——而且只判『证据够不够』，不判『结论对不对』。后者需要领域知识，前者只需要逻辑。」
