# T5-0 · 泛化三件事：Domain Pack 剥离 + 通用工具层 + 第二领域验证

日期：2026-11-13 ｜ 状态：✅ 已完成

## 动机

项目被评价为"偏运维侧"。但真正值钱的机制（容灾链、预算、门禁、证据回溯、评测回归、span）
全部领域无关——偏运维的是**知识的位置**：5 类定义、few-shot、规则基线硬编码在
`agents/classifier.py` 里。本次改造把知识剥成插件，并补上通用 Agent 的标志能力（工具调用）。

## 1 · Domain Pack：引擎与领域知识分离

```
app/domains/
├── __init__.py      # DomainPack 契约：role_intro / classes / few_shot / rule_baseline
├── ssrm/            # 供应商运维领域（taxonomy.py / rules.py / pack.py）
└── csa/             # 电商客服领域（第二实例）
```

- `agents/classifier.py` 重写为**领域无关引擎**：通道编排、输出校验、证据门禁、置信度门禁；
  知识全部来自注入的 pack；
- `__init__.py` 的 docstring 就是 pack 契约，实现不许偏离；
- 面试话术升级："分类引擎是领域无关的，接新领域 = 写一个 pack + 一套评测集，引擎零改动。"

## 2 · 通用工具调用层（为什么不 用 Function Call / LangChain）

`app/core/tools.py`（~80 行，零依赖）+ `app/core/builtin_tools.py`（3 个内置只读工具）：

- **不用 Function Call**：项目全线走 JSON mode（glm-4-flash 不支持 response_format，
  且 JSON mode 跨 Provider 行为一致、可评测）；混用两套协议 = 双倍评测面；
- **不用 LangChain AgentExecutor**：它把"选了什么、为什么、参数是什么"埋进抽象——
  与本项目"每步可观测可门禁"的立身之本冲突；
- **三道关**（与分类器同一门禁哲学）：白名单（LLM 编造的工具名到此为止）→
  schema 校验（必填/类型/声明外参数）→ 置信度门禁（<0.7 不执行）；
  `read_only=False` 的工具一律拒绝自动执行（副作用工具接权限系统之前宁可空手而归）；
- 端点：`GET /tools`（注册表清单）、`POST /tools/ask`（选工具→校验→执行）。

实测（glm-4-flash）：
- "知识库里有多少条工单" → 正确选 `kb_stats` 并执行，conf 1.0；
- "查 duplicate_submit 类型的 5 条历史事件" → 正确选 `query_incidents`，参数类型正确；
- "把生产服务器重启一下" → `tool: null`，不选不执行（超出注册表职责，转人工）。

## 3 · 第二领域实例（迁移的最硬证明）

`domains/csa/`：电商客服工单分类（退款纠纷 / 物流延迟 / 售前咨询 / 发票开具 / 账号安全），
知识面与 SSRM 完全正交——没有系统拓扑、没有错误码，判断依据是用户原话。

| 通道 | CSA 客服域 | SSRM 运维域 |
|---|---|---|
| 规则基线 | 30/30（100%） | 30/30（100%） |
| LLM 容灾链 | **29/30（96.7%）** | 100% |
| 平均延迟 | 2803 ms | ~3.7s |

规则迭代过程本身就值得讲：初版 80%（6 个混淆），修正后发现一个比关键字更强的判据——
**没有订单（order_status=none）就不可能是售后类**。领域知识的演化全部发生在 pack 目录内，
引擎零改动。

评测入口：`python -m app.evaluation.eval 30 --domain csa [--rule]`

## 已知边界

- 工具层是单步选择（选一个工具执行一次），多步规划（工具链）未做——那是 T5 LangGraph 的议题；
- CSA 困难样本混在全量集里（口语化），没有独立 hard 集；
- `POST /tools/ask` 是独立演示端点，尚未接入 /assist 的对话流。


## 追记：第三领域 CREDIT——一次反向验证（2026-11-13）

对接蚂蚁信贷风控 Agent 岗后新增 `app/domains/credit/`（消费信贷进件风险分类：
欺诈嫌疑/多头共债/还款能力不足/资料不全/正常放行，结构化风控字段 + 用途说明文本）。

### 这个领域给出的不是又一个"迁移成功"，而是反向验证

| 通道 | 准确率 |
|---|---|
| 规则基线（硬阈值策略） | 96.7%（29/30） |
| glm-4-flash 全量 LLM 通道 | **60.0% ~ 66.7%** |
| **rule_first 混合（规则先行 + 灰区 LLM 仲裁）** | **96.7%**（延迟 204ms 均值） |

1. **LLM 跑不过规则**：信贷是"策略即硬规则"领域，月供/收入比是算术题、查询次数 ≥8 是
   阈值题——小模型做这两件事都不可靠（把 40000/12 算错、忽略 ≥8 阈值、把"选购一辆
   代步车"判成资料不全）。这不是模型问题，是**任务形态问题**：硬阈值分类本就该规则做；
2. **引擎因此长出 rule_first 能力**：pack 声明 `rule_first=True` → 规则给出明确结论直接
   采用（source=rule_primary），落 unknown（灰区）才升级 LLM 仲裁（source=llm_arbiter）。
   引擎机制按领域特性反向演化，但演化被限制在引擎的一个开关里，pack 契约不变；
3. **灰区仲裁的安全网实测**：唯一升级的 CRA-016（dti 0.68 边界带）LLM 也判错
   （multi_debt → repayment_risk），但 evidence_score=0.125 触发证据门禁 →
   置信度压至 0.4 → needs_human_review=True——**错的结论到不了业务**；
4. **对齐 JD 的叙事**："将业务流程中的问题建模、转化为 Agent 可自动化交付的作业流程"
   ——这个实验本身就是建模过程：先假设 LLM 主导，评测数据否决，改为主从编排；
   同时拒贷可解释/可申诉的监管要求 = 证据可回溯门禁的业务价值证明。


## 再追：评测集扩到 300 条 + 灰区的指标设计问题（2026-11-13）

`scripts/gen_credit_dataset.py`（固定种子）：30 条手工金样本 + 270 条参数化合成 = 300 条，
每类 60 条，其中 9 条为**灰区形态**（dti 0.60~0.70 且查询<8，规则按设计落 unknown）。

| 口径 | 数字 |
|---|---|
| 规则强制通道（300 条） | 291/300 = **97.0%** |
| **明确区准确率**（扣除 9 条设计灰区） | 291/291 = **100%** |
| 混合通道（规则先行+灰区仲裁，300 条） | 291 直判全对 + 9 灰区全部正确升级 |
| 灰区仲裁与标注的一致率 | 1/9（模型系统性倾向 repayment_risk，标注倾向 multi_debt） |
| 平均延迟 | 192ms（291 条 0ms + 9 条 LLM 仲裁） |

### 两个超出"跑个分"的发现

1. **生成器 bug ≠ 规则 bug，但都值得修**：首轮 300 条跑出 91.7%，调试发现 25 个错误里
   17 个是生成器约束写错（月供公式算错、material 样本金额未钳制），2 个是规则话术词表
   缺口（"特殊通道/不看征信"）——评测集规模一大，**它同时测规则和测自己**，这正是扩数据的
   价值：30 条测不出"月供公式在边界档位分布下失效"这种问题；
2. **灰区没有 ground truth，指标要分层设计**：灰区 9 条上"模型 vs 标注"分歧 8 条，
   但模型高度一致（全判 repayment_risk，依据 dti）、标注也有一致逻辑（依据"借新还旧"
   用途）——这不是谁错了，是**边界带上两种人类可信判断的分歧**。业务上两类都进信审决策、
   处置动作相同，分歧无业务代价。诚实口径是三层：明确区 100%（规则的价值）、灰区 100%
   正确升级（机制的价值）、灰区标注一致率 1/9（**标注的边界，不是模型的错误**）。
