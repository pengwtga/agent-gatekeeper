# F04 上下文装配与压缩

迭代：I2 ✅ 已实现 ｜ 依赖：F02 ｜ 代码：`oncall/context.py`

**实现状态（I2）**：压缩 = 事实表全量保留（③ 段，本身就是压缩产物）+ 步骤原文只留最近 3 步 + 被移出步骤在 prompt 里标注去向（「更早 N 步已压缩：结论在事实表，原文见 trace」）。规则段钉在 system 永不压缩，单测断言任何一轮都在。I1 设计的 token 估算触发器简化为结构化常量（步数 ≤12 时全量事实远小于窗口，无需动态触发）——这个简化在 12 步上限下是安全的。

## 1. 目标

每一步给模型**刚好够用的**上下文：不爆窗口、不丢结论、不让早期噪声淹没当前判断。

## 2. 装配的六段（顺序固定）

| 段 | 内容 | 预算占比 | 说明 |
|---|---|---|---|
| ① 角色与规则 | 你是 SSRM 值班排障助手；只读优先；写操作必须申请 | 8% | 稳定前缀，**利于前缀缓存** |
| ② 任务 | 现象原始描述 + incident_id | 5% | 不加工，原文 |
| ③ 已确认事实 | 结构化列表（field / value / 来源 ref） | 25% | 只放被工具证实过的 |
| ④ 未决假设与已排除 | 两列，各带一句理由 | 10% | 防止模型原地绕圈（与 F02 的无进展检测互补） |
| ⑤ 最近 N 步 | 最近 3 步的工具调用与结果（已截断） | 35% | 原文只留最近几步 |
| ⑥ 可用工具与输出契约 | schema + 输出 JSON 结构 | 17% | 契约每次都给，别靠模型记 |

**为什么 ③④ 单独成段而不是留在对话历史里**：历史是线性的，模型要自己「回头看」才能知道已排除了什么；显式两列等于帮它做了归纳。实测里这一步比单纯压缩更能减少重复调用。

## 3. 压缩（compaction）

### 触发
- 估算 token > 窗口 × 60%，或
- 步数 > 6（长尾任务主动压一次）

### 策略：**摘要成事实，不留摘要成散文**

把最早的 K 步压成：

```
已确认（可引用）：
- xflow.callback_url = http://old-ssrm/... （来源 cfg:xflow）
- 回调实测 404 （来源 log:2026-11-17T10:12）
已排除：
- EA 侧任务队列积压（来源 metrics，p95 正常）
未验证：
- 新域名是否已在网关放行
```

三条硬规则：
1. **每条必须带来源 ref**，否则压缩就是在制造幻觉
2. **原文不删**，只从上下文里移出，`full_ref` 指向 trace（可回查）
3. **数值原样保留**，不做「大约」「略微」这类模糊化

### 不做什么
- 不做逐字摘要（丢字段名就等于丢证据）
- 不做「保留最后 N 轮」的滑动窗口（会丢掉最早的根因线索——恰是最值钱的那条）

## 4. 装配失败的三种表现（可诊断）

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 反复查同一个工具 | ③ 段没把已知事实写清 | 检查事实抽取是否丢字段 |
| 结论无证据 | ⑤ 段把原文截得太狠 | 放宽最近 2 步的截断阈值 |
| 无视约束（直接调写工具） | ① 段被压缩掉了 | 规则段永不参与压缩（钉在头部） |

## 5. 取舍

- **不做 RAG 式上下文检索**（把历史步骤丢向量库再召回）：步骤少（≤12），全量放前面更可控，召回反而引入不确定性。
- **不做多轮对话历史**：CLI 单次运行无多轮；多轮在 `/assist`（F12）。
- **前缀稳定优先于信息密度**：①⑥ 两段一字不改，才能吃到 provider 的前缀缓存（成本差数倍）。

## 6. 验收

1. 同一任务，开/关压缩对比：token 降【待实测】%，pass@1 不降
2. 构造「早前事实被压掉」的用例：必须仍能从 ③ 段引用到该事实（有 ref 可点）
3. 规则段在 12 步全程存在（单测：每轮装配结果都包含规则签名）
4. 压缩后 JSON 仍可解析（压缩输出本身必须是结构化事实，不是自由文本）

## 7. 面试一句话

「压缩不是把对话摘要短一点，而是把对话变成事实表——每条带来源、数值不改写、原文留在 trace 里可回查。做错这一步，agent 会开始用自己编的事实推理。」
