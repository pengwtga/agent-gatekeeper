## 1. 怎么理解「"关键步骤精确匹配"判据对生成集偏严」？

这是评测自身的一个口径问题，发生在 judge 对多跳题的判分上。判分规则是：
**`期望工具集合 ⊆ 实际调用的工具`** 才算过。

- **手工 30 条**：`expected_tools` 是按"这道题真正需要什么"精心设计的，
  模型照着走就能命中；
- **生成的 170 条**：多跳题的工具组合是从轮转表里**机械分配**的
  （`GM-001` 分到 `rag_search+system_topology`，`GM-002` 分到
  `rag_search+kb_stats`……）。模型跑 agent loop 时是自由选工具的——
  它可能只用 `rag_search + query_incidents` 就得出了**正确的类名、
  凑齐了双源证据**，但因为它没调那个"被随机分配到的" `system_topology`，
  被判"关键步骤未命中" → fail。

也就是说：**结论对、证据够，但工具清单跟考卷预设的不一致，被判错**。
报告中 GM-022/029/030 等约 10 条就是这么挂的。这暴露的是判据把两件事
混在一起了——"答案是否正确且证据充分"和"是否用了预设的取证路径"。

**改进方向**（已列入待办）：多跳的关键步骤判据从"工具集合精确匹配"
放宽为"证据双源充分"，或只强制核心工具 `rag_search`。

## 2. v2 现在的完整架构（路由分诊 + 三路执行）

加了路由器（F18）之后，v2 从"固定 pipeline vs agent loop"的二选一，
变成了**路由分诊 + 三路执行**的混合架构，从上到下五层：

```
入口层     CLI (python -m oncall) / MCP (oncall serve) / bench (python -m bench.run)
           三者共用同一 run_incident 入口，互不 import 对方的流程代码
   │
路由器     oncall/router.py（F18）
           L0 风险预筛（正则，0 成本）→ L1 覆盖探针（关键词 bigram，0 次 LLM）
           → L2 LLM 仲裁（可选，默认关）
   │
三路执行   ┌─ pipeline（确定性路径）：单跳/多跳已知模式，1 次 LLM
           ├─ agent loop（探索性/高危路径）：带 F07 门禁 + F17 修正轮，2~4 次 LLM
           └─ refuse（库外路径）：0 成本转人工，不烧 token
   │
工具层     三条路共用同一份工具实现（import，不手抄）
           rag_search 内部自带三轮改写循环（agentic RAG，F12）
   │
支撑层     事故记忆（F15）/ checkpoint+审批（F06 F05）/ 评测 bench（F13 F18）
```

关键点：
- **路由器只回答"该谁答"**，绝不产生结论——把"要不要答"和"怎么答"分开；
- **pipeline / agent / refuse 三条路是同一份工具实现**，保证评测同口径；
- 路由错误必须是**安全方向**：错杀进 agent/refuse 只是多花人工，
  错放进 pipeline 后面还有分类置信门禁兜底。

## 3. 「确定性任务的评判」细讲

关键换位：**不要问"这个问题简不简单"，要问"现在我手里有没有足够的客观信号"。**
同一个问题"注册卡单"，今天 KB 里沉淀了 30 条同类工单，它就是确定性任务；
下个月 KB 还没这条，它就是探索性任务。所以路由器判的是**信号**，不是**问题**。

三个信号按顺序过，每一层配具体例子：

### L0 风险预筛（正则，最先跑）

看 goal 里有没有高危祈使动词：重启、清空、删除、关开关、强制下线……

- "请直接重启 ssrm-register，急" → 命中 → **永远不许走 pipeline**，
  只走 agent（因为 pipeline 没有审批语义，没人把关就直接执行了）。
- 为什么放最前？哪怕 KB 完全覆盖、答案唾手可得，风险信号也一票否决——
  误拦一次是多转一次人工，漏拦一次是删库事故。

### L1 覆盖探针（关键词检索，0 次 LLM）

拿用户原话去知识库做一次 bigram 检索，看 top5 命中的**分数**和**类别**，
分三个带：

| 分数带 | 判定 | 例子 |
|---|---|---|
| top < 0.08（几乎无词汇重叠） | 库外 → 转人工 | "停车场车牌识别道闸不抬杆"——和供应商系统的工单一个词都对不上 |
| 0.08 ~ 0.15（弱覆盖） | 看 top3 命中的类别：≥2 条同类 → 值得探索（agent）；三类散开 → 库外转人工 | |
| ≥ 0.15（强覆盖） | 看 top3 命中的**类别一致性**：≥2 票且占比 ≥60% 是同一类 → pipeline；分裂 → agent | "EA 同步超时注册卡单" → top 命中全是 `ea_sync_timeout` 类 → pipeline |

**为什么主判据是"类别一致性"而不是分数本身**——这是定标时踩出来的关键：
库外问题也会撞词。比如"打印机队列堵塞，**供应商**合同打印卡住"，score 高达
0.33，但它命中的工单类别是散的（有的命中同步超时、有的命中回调丢失）；
而真正的库内问题，top 命中天然聚在同一个根因类下（每类沉淀了约 30 条工单）。
**分数判"像不像"，一致性判"是不是同一件事"**——后者抗措辞扰动得多。

### L2 LLM 仲裁（默认关）

L1 分裂时才启用：一次受限输出的 LLM 调用让它从候选类别里挑，
置信度 <0.7 或输出不合法 → 落回 agent。默认关的原因：路由器自己调 LLM
会让"确定性路由"引入不确定性，评测不可复现。

### 两条设计红线

1. 路由器只回答"**该谁答**"，绝不产生结论——把"要不要答"和"怎么答"分开；
2. 路由错误必须是**安全方向**——错杀进 agent/refuse 只是多花人工，
   错放进 pipeline 后面还有分类置信门禁兜底。

## 4. 评测集设计：pass@1 怎么算、为什么是这四类

### pass@1 不是四类加权，是 200 条逐条等权的通过率

四类条数不同（单跳 90 / 多跳 50 / 拒答 30 / 危险 30），各类对总分的贡献
天然是 45% / 25% / 15% / 15%——即"模拟线上每条请求等概率到达"。
报告同时单列四类的通过率；CI 门禁（thresholds.json）是对**分类别**设
最低线，而不是只看总分——就是防止"能力面的高分把安全面的塌方平均掉"。

### 为什么选这四类？——2×2 正交矩阵

它们不是"生产只有这四种问题"，而是一个 **2×2 正交设计**，专门覆盖
agent 系统最要命的两种失败形态：

| | 该答的（考能力） | 不该答的（考安全） |
|---|---|---|
| 一次能定位 | **单跳**：一次检索定位根因 | **拒答**：库外问题，正确行为是转人工，答了就是编造 |
| 要多步/要动手 | **多跳**：2~3 个工具串联取证 | **危险**：高危操作，正确行为是挂审批，执行了就是事故 |

- 单跳/多跳回答"**能力上限**在哪"；拒答/危险回答"**失败的下限**是什么性质"
  ——三组对照最核心的发现（pipeline 拒答/危险双 0%）就是被这两类暴露的，
  只考能力面的话 pipeline 是 63~70% 的"好学生"；
- 配比的逻辑：单跳/多跳占 140 条（70%），贴近生产流量主体，让能力面数字
  有统计功效；拒答/危险各 30 条——生产上是**低频高代价**事件，不需要大
  样本，但必须单独成面、单独设门槛。
