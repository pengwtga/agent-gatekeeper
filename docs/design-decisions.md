# 设计决策 FAQ · 面试追问沉淀

记录面试准备中被追问、且答案对系统设计有真实约束的问题。每条按「问题 → 答案 → 系统里的落点」组织。

---

## Q1 · 为什么根因分类不需要 RAG，而值班助手需要？

**答案：选型依据是知识的形状，不是 RAG 时髦。RAG 不是能力增强的默认项，是知识管理的方案。**

| | 根因分类 | 值班助手 |
|---|---|---|
| 知识形态 | 5 类定义 + 2 组 few-shot，不到 1K token，**小而稳定** | 30+ 条工单处置细节，**长尾且持续增长** |
| 知识更新方式 | 改 prompt → 走版本化 + 回归评测 | 工单回流进 KB → 运营资产，不应改代码 |
| 输出要求 | **一致性**（同类事件同标签） | **可溯源**（based_on 引用真实工单） |
| 检索的副作用 | 引入不确定性，反而让输出抖动 | 提供 grounding，防止编造操作 |
| 触发频率 | 机器高频触发，检索多一档延迟和故障面 | 人工触发，几秒可接受 |

一句话：**知识放得进 prompt 就放 prompt（in-context + 回归评测）；知识放不进、长得快、要引用溯源，才值得付检索的成本。**

追问「分类以后要不要上 RAG」：当类别扩到几十类、或要求"新增根因不发版"时，可以把**类别定义本身做成可检索的**（检索 top-k 类别定义 → 塞 prompt → 分类）。但那是规模驱动，当前 5 类上 RAG 是过度设计。

## Q2 · 归因不在当前 5 类里怎么办？要增加根因吗？

**答案：unknown 是体系演化的输入，不是异常。但"出现"不触发加类，"重复出现 + 有独立处置"才触发。**

### 系统现状

- LLM 通道：prompt 强约束 5 个枚举值，输出非法类别 → `_validate_class` 打回 `unknown`；
- 规则基线：兜底匹配不上 → `unknown + confidence 0.2 + needs_human_review`，处置建议就是"转人工，归因后沉淀为新规则"；
- 设计哲学：**宁可说不知道，不把八成把握包装成十成**。

### 是否新增类别的判据

> **它有没有独立的处置动作？**

- 处置与现有类**不同**（如"供应商材料不合规"→ 退回补材料，5 类覆盖不了）→ 该加新类；
- 处置与现有类**相同**，只是现象换说法 → 是现有类的子模式，不加类，往该类 few-shot / 评测集加样本。

分类的目的是驱动处置，**没有独立处置的类别没有存在价值**——这条防"类别爆炸"（根因表从 5 类涨到 40 类，模型和人都会崩）。

### 新增一个类的完整流程

1. **归因确认**：unknown 样本人工归因，确认是新模式而非现有类变体；
2. **定义**：名称 + 定义 + 标准处置，写清与最相近类的边界；
3. **few-shot**：加一组与最易混淆现有类成对的示例（分类难点永远在边界）；
4. **评测集**：加正样本 + 边界对照样本；
5. **回归**：全量跑评测，确认旧类准确率没有因边界移动下降——没有回归集就加类等于盲改；
6. **监控**：盯新类占比 + **unknown 率下降**——它是这次演化成功的量化证据。

### 指标落点（已实现）

unknown 率已进指标体系（T2-3 扩展）：

- `metrics.record_class()`：分类输出分布计数（LLM 与规则通道都算，规则通道也会产 unknown，漏记会低估漏斗入口）；
- `/metrics` 的 `classification` 字段：`decisions / unknown_count / unknown_rate / by_class`；
- 可观测「质量分析」页新增「根因分类分布」卡片，unknown 单独标色；
- `python -m app.eval` 输出增加 `unknown 判定` 行。

**归因口诀：模型坏了看降级率，体系旧了看 unknown 率——两个指标分开看，别把体系覆盖率问题误诊成模型质量问题。**
