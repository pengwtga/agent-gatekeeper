# T3-0 · RAG 检索评测：让"检索质量"和"阈值 0.55"有数字支撑

日期：2026-11-13 ｜ 状态：✅ 已完成

## 动机

面试里三个必被追问、以前只能含糊回答的问题：

1. "30 条知识库，检索有意义吗？"
2. "Recall / MRR 是多少？"
3. "`rag_min_score = 0.55` 怎么定的？"

以前答案是"体感"，现在有评测集、有指标、有阈值扫描表。

## 交付物

| 文件 | 内容 |
|---|---|
| `app/rag_eval.py` | 评测脚本：Recall@1 / Recall@3 / MRR@8 + 按根因类别分组 + 阈值扫描 |
| `data/rag_queries.jsonl` | 常规集：30 条值班口吻提问 → 应命中的 ticket_id（对 symptom 改写，非原句复制） |
| `data/rag_queries_hard.jsonl` | 困难集：10 条同义词替换/去黑话的提问（"xFlow"→"那边"、"对账任务"→"核对活儿"），专打关键词召回的语义鸿沟 |

评测集设计原则（回应"自己出题自己答"）：
- **问题与 symptom 不同词面**：常规集改写句式，困难集系统性替换领域词，留有字面重叠的通道也测不出通道差异；
- **覆盖全部 5 类根因**，每条查询的 relevant 工单人工指定并进 git，可复核；
- **困难集对照常规集**：一个测"能不能检索"，一个测"词面不通时还能不能检索"。

## 结果

常规集（30 条）：

| 通道 | Recall@1 | Recall@3 | MRR@8 |
|---|---|---|---|
| 关键词召回 | 100% | 100% | 1.000 |
| 关键词 + LLM 重排 | 100% | 100% | 1.000 |

困难集（10 条）：

| 通道 | Recall@1 | Recall@3 | MRR@8 |
|---|---|---|---|
| 关键词召回 | 90% | 100% | 0.950 |
| 关键词 + LLM 重排 | **100%** | 100% | **1.000** |

**通道对比结论（面试重点）**：30 条规模下关键词基线本身就很强（字面重叠足够），
但困难集上它有一个 Recall@1 失手——正是语义鸿沟型提问；LLM 重排把这个失手修回来了。
"为什么降级模式是关键词召回 + LLM 重排而不是纯关键词"，从此是**测量驱动的决策**，不是拍脑袋。

阈值扫描（常规集，关键词模式分数 = 查询字符覆盖率，可解释）：

| 阈值 | 查询覆盖 | 留存结果精度 |
|---|---|---|
| 0.4 | 97% | 29/36（81%） |
| 0.5 | 77% | 23/24（96%） |
| **0.55** | **73%** | **22/22（100%）** |
| 0.6 | 60% | 18/18（100%） |

**0.55 的辩护口径**：它是"精度掉下来之前"的最高覆盖点（0.5 开始漏入错例，0.55 起精度 100%），
代价是 27% 的查询拿不到检索结果、转"建议人工"——这是采信门禁的设计意图，不是缺陷。

## 已知边界（写在明处）

1. LLM 重排模式的 score 是排名近似（1.0 递减 0.1），不是语义相似度——
   **阈值门禁只在分数可解释的通道上生效**。重排通道的"低置信"判断依赖 LLM 总结阶段的 confidence；
2. 评测集 30+10 条，单次波动大，看趋势不看小数点；扩到百条级再谈统计显著性；
3. 常规集对两条通道都 100%，说明它只能做**回归防线**（防止改动检索代码后退化），
   区分能力靠困难集——这也是为什么两个集都要存在。

## 验收

```bash
.venv/bin/python -m app.rag_eval --rerank    # 对齐线上降级模式（调 LLM）

```

## 补记：检索规模 benchmark（2026-11-13）

回应"知识库不止 30 条时，暴力余弦还适用吗"——用随机归一化向量实测（余弦计算量与
向量取值无关，延迟反映真实矩阵乘开销；dim=512 对齐 embedding-2，每档 200 次查询）：

| 知识库规模 | 向量矩阵内存 | p50 | p95 | max | 结论 |
|---:|---:|---:|---:|---:|---|
| 30 | 0.1MB | 0.01ms | 0.01ms | 0.42ms | 当前规模 |
| 100 | 0.2MB | 0.02ms | 0.04ms | 0.11ms | 余量充足 |
| 1,000 | 2.0MB | 0.08ms | 0.16ms | 1.22ms | 设计舒适区 |
| 10,000 | 19.5MB | 0.91ms | 4.39ms | 7.88ms | 仍可接受 |
| 50,000 | 97.7MB | 5.82ms | 9.89ms | 13.02ms | 接近换挡 |
| 100,000 | 195.3MB | 14.18ms | 44.88ms | 78.47ms | 应换 ANN（Faiss/HNSW/pgvector） |

**解读**：
1. 千条级毫秒内、万条级个位数毫秒——`InMemoryVectorStore` docstring 里写的 "<1000 条无需
   Faiss" 其实保守了，**架构换挡点在十万条级**，人工沉淀的值班知识库十年也未必到；
2. 对照整条链路：一次 glm-4-flash 调用 p95 ≈ 4200ms，检索开销在 1 万条规模下占比 <0.2%，
   **瓶颈从来不在余弦相似度**——规模上去先撞墙的是阈值失准（0.55 需重扫）、KB 治理
   （去重/淘汰/metadata 过滤）和 embedding 预算，这三个是数据/运营问题不是检索算法问题；
3. 退路已埋：`InMemoryVectorStore` 接口按向量库对齐（add/search/save/load），换 Faiss 或
   pgvector 只动一个文件，`rag_assistant` 零改动。

### 再补：全检索管线基准（真实工单扰动扩充，2026-11-13）

回应"随机向量是不是只测了内核"——用真实 30 条工单扰动扩充（改 id + 标题加变体标记 +
正文追加一句，保持真实中文文本形态），实测**关键词召回阶段**（线上降级模式的第一步，
纯 Python O(N) 扫描，不含 embedding API 与 LLM 重排——这两项不随 KB 规模增长）：

| 知识库规模 | 关键词召回 p50 | p95 | max | 对照：余弦内核 p50 |
|---:|---:|---:|---:|---:|
| 30 | 0.09ms | 0.11ms | 0.34ms | 0.01ms |
| 1,000 | 2.92ms | 3.52ms | 7.85ms | 0.08ms |
| 10,000 | 28.34ms | 34.73ms | 64.08ms | 0.91ms |
| 50,000 | 151.97ms | 191.55ms | 278.87ms | 5.82ms |

**新结论**：
1. **先到的瓶颈不是余弦，是关键词召回**——纯 Python 逐条扫描比 NumPy 矩阵乘慢 ~30 倍；
   万条级 28ms 仍可接受（对比 LLM 调用秒级），十万条级 150ms+ 就该换结构了；
2. 这组数字把优化优先级排清楚了：真要扩规模，第一刀优化关键词扫描（jieba 分词 +
   倒排索引，或干脆修好 embedding 配额走向量模式），而不是急着上向量数据库；
3. 测试方法学：内核基准（随机向量）量"算法随规模的伸缩项"，管线基准（真实文本扰动）
   量"工程实现的真实成本"——两个一起才构成完整的规模答案。

```bash
.venv/bin/python -m scripts.vector_bench              # 余弦内核全梯度（30 → 100k）
.venv/bin/python -m scripts.vector_bench --quick      # 内核只跑到 1 万条
.venv/bin/python -m scripts.vector_bench --pipeline   # 真实工单扩充 + 关键词召回全管线
```
