# T4-01 · 切块实验：resolution 参与检索是否有收益 → 结论：不做

> 实验脚本：见本文 §2（纯离线，未改任何产品代码）
> 对应任务清单：T4-1（原方案「30 条 → 90 chunk 按字段切三块」）

## 1. 原方案的前提已经不成立

任务清单（2026-11-10）写 T4-1 时知识库是 30 条单份向量，`resolution` 只参与生成不参与检索。
此后 T5-01 把 KB 扩到 ssrm 150（30 手工 + 120 同簇变体）/ csa 100 / credit 120，
且评测已有 strict/cluster 双口径与三域定标阈值。两个前提变了：

1. 条目是**单主题工单**，不是需要切分的长文档——切块（symptom / root_cause /
   resolution 三块）会把一个簇拆成 3× 条目，破坏 cluster 语义，答案引用也要回到整段；
2. 检索指标已经很高（ssrm 簇级 99.3%），切块的潜在收益空间极小。

## 2. 实验：索引文本四个变体 × 三域

比切块更保守的实验先做：不动 chunk 结构，只把 `root_cause` / `resolution`
拼进索引文本（title+symptom 为现状基线），看检索指标变化。

| 域 | title+symptom（现状） | +root_cause | +resolution | +全部字段 |
|---|---|---|---|---|
| ssrm（150 查询） | **99.3% / 100% / 0.997** | 99.3% / 100% / 0.997 | 98.7% / 100% / 0.993 | 98.7% / 100% / 0.993 |
| csa（40 查询） | **100% / 100% / 1.000** | 100% / 100% / 1.000 | 97.5% / 100% / 0.988 | 97.5% / 100% / 0.988 |
| credit（40 查询） | **87.5% / 97.5% / 0.927** | 87.5% / 97.5% / 0.927 | 52.5% / 82.5% / 0.668 | 52.5% / 82.5% / 0.668 |

（簇级 R@1 / R@3 / MRR@8；打分器为 T5-01 的 bigram 字符覆盖率）

**结论：全线变差，credit 域崩到 52.5%。** 原方案被数据否决。

## 3. 为什么会变差（机制解释，面试可讲）

字符覆盖率分母是**查询**的 gram 数（`|q∩d| / |q|`），扩文档字段只会让每个文档的
分数不降；但 ranking 靠的是**相关文档与无关文档的分差**：

1. `resolution` 充满通用运维/客服词（排查、确认、恢复、联系），无关文档也大量命中
   → 无关文档的分数被系统性抬高；
2. 查询是对 **symptom** 的改写——相关信号本来就集中在 title+symptom，
   扩进来的字段对相关文档是噪声、对无关文档是「送分」；
3. 近重复簇内所有变体同涨同跌，簇内区分度不变，簇间区分度被压缩。

credit 域最惨的原因：催收话术条目的 resolution 高度模板化（话术结构雷同），
无关条目借模板词「蹭分」最严重。

## 4. 决策与边界

- **决策**：不切块、不扩索引文本。`resolution` 继续只参与生成（LLM 总结的上下文），
  不参与检索——这个原设计被实验证明是对的；
- 何时重新评估：KB 出现**单条多主题**的长文档（如 SOP 全文入库）时，切块才有意义；
  届时评测口径需要同步设计（chunk→母条目的簇映射）；
- 本任务零产品代码改动，纯实验 + 结论存档。
