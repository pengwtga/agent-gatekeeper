# T1-3 needs_human_review 收口到后端

## 1. 问题

门禁判定（置信度 < 0.85 → 人工确认）原来存在于**三处**：

1. 后端 `classifier`：T0-3 起所有路径都输出 `needs_human_review` ✅
2. 前端 React `Playground.jsx`：`data.needs_human_review ?? confidence < 0.85` —— 字段缺失时**前端自己算**
3. 前端内联页（main.py）：同样的 `?? (c < 0.85)` 兜底

「字段缺失时前端兜底计算」意味着：**后端改了阈值，前端的兜底不会跟着变**。
判定逻辑复制两份，改一处忘一处是必然事故——而且错的那份是用户直接看到的。

## 2. 判断

判定逻辑必须**单一来源**。前后端对同一个业务门禁各自持有一份阈值，不是冗余备份，
是两个会漂移的真相。前端只应该渲染后端给的决定，而不是重新做决定。

这条的原则和 T0-3 一致：能被代码判定的，不要让两个地方各判一次。

## 3. 方案取舍

| 方案 | 取舍 |
|---|---|
| ✅ 前端只读字段，缺失时 fail-safe 转人工 | 单一来源；缺失按保守处理 |
| ❌ 前端 `?? (c < 0.85)` 兜底 | 就是问题本身 |
| ❌ 前端从 /health 拉阈值自己算 | 阈值同步了，但判定逻辑仍在两处 |

fail-safe 方向的选择：字段缺失 → `needs_human_review !== false` → **默认转人工**。
门禁宁可误报（多一次人工确认），不可漏报（自动处置了不该自动处置的）。

## 4. 改动

- `frontend/src/pages/Playground.jsx`：
  `data.needs_human_review ?? confidence < 0.85` → `data.needs_human_review !== false`
- 文案去掉硬编码的「（0.85）」——阈值属于后端配置，前端展示不该写死数字
- `main.py` 内联页面同步修改（T6-1 会删，先保持一致）
- `Tags.jsx` 的 0.85/0.70 **保留**：那是展示配色（三档颜色），不是门禁判定；
  注释已明确「判定唯一来源是后端 needs_human_review」

## 5. 验收

```
grep -rn "0.85" frontend/src/
→ 仅 Tags.jsx 展示配色 1 处（含「非判定」注释），决策逻辑 0 处
后端三条路径（LLM 成功 / LLM 降级规则 / 纯规则）的响应 JSON 均含 needs_human_review
  5.2/4.3/6.1 三项验收 PASS
```

## 6. 边界

- 旧版前端（缓存未刷新）拿到的字段齐全，行为一致，无兼容问题
- 「0.85 不再出现在前端」的代价是文案里不显示具体阈值；若产品要求显示，
  正确做法是后端在响应里带 `gate_threshold` 字段，而不是前端写死

## 7. 面试讲法

> 我发现门禁判定在后端和前端各有一份——前端用 `?? (c<0.85)` 兜底。
> 这种「看起来更健壮」的兜底其实是隐患：后端调阈值，前端永远不会跟着变。
> 收口原则是判定单一来源，前端缺失字段时按保守方向处理（默认转人工），
> 因为门禁误报的代价是多一次人工确认，漏报的代价是错误自动处置。
