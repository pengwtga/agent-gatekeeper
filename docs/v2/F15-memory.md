# F15 事故记忆

迭代：I4 ｜ 依赖：F13 ｜ 代码：`oncall/memory.py`

## 1. 目标

让「上次同类事故是怎么解决的」在**下一次**自动出现在上下文里，而不是靠人记。

## 2. 三类记忆，v2 只做第三类

| 类型 | 载体 | v2 做不做 |
|---|---|---|
| 短期 | 上下文窗口 | 由 F04 管 |
| 情节（episodic） | 本次 run 的 facts/steps | 由 F06 落库，不做跨 run 检索 |
| **程序性（procedural）** | 事故 → 结论 → 动作 的映射 | **做这个** |

**为什么不做「全库向量检索历史对话」**：检索噪声会污染上下文，比没有记忆更糟。事故记忆的相似性是「同现象」，不是「语义相近」——而「同现象」在 v1 里已经有现成结构：**30 簇**。

## 3. 写入（run 结束时）

```json
{"incident_id": "INC-2026-1117", "cluster": "callback_lost",
 "fingerprint": "注册卡单+xflow回调404", "conclusion": "...",
 "action": "更新回调配置并重放", "outcome": "done|needs_human|failed",
 "run_id": "r-...", "created_at": "..."}
```

三条纪律：
1. **只写已验证的**：`status=ok` 且过了传感器才写；`needs_human` 写进去会把未验证结论变成下次的“经验”
2. **写簇而不是写文本相似**：簇来自 KB（`root_cause_class`），保证与检索同一套坐标
3. **记 outcome**：动作做了但没解决，也要记——「这条动作对此现象无效」同样是知识

## 4. 读取（装配时）

在 F04 的 ③ 段后插入一段「历史同类」：

```
历史同类（同簇，最近 3 条）：
- 2026-11-03 现象：注册卡单+回调 404 → 结论：回调地址陈旧 → 动作：更新配置并重放（已验证）
- 2026-10-21 现象：注册卡单，回调 200 但任务未建 → 结论：EA 侧队列积压 → 动作：等 15min（已验证）
```

**注入的是「结论 + 动作 + 结果」，不是原文**。给模型看原文等于把上次的噪声再灌一遍。

## 5. 排序与截断

- 同簇内按「时间近 + outcome=ok」排序，取 3 条
- 跨簇不取（跨簇的相似性是假相似，v1 的 bigram 实验已经证明簇内/簇间差异明显）
- 每条 ≤ 60 字，整段 ≤ 200 token

## 6. 取舍

- **不引入 embedding**：30 簇规模，簇 ID 就是最好的索引；上向量库是过度设计（也无法解释「为什么召回这条」）。
- **不做记忆衰减/遗忘曲线**：用时间排序 + 限 3 条已经达到效果，加权公式是无根据的复杂度。
- **不做用户级个性化**：这是团队工具，不是个人助手。

## 7. 验收

1. 重复事故（5 条同簇变体，第二次出现）：平均步数下降【待实测】%
2. 错误记忆不污染：故意写一条 `outcome=failed` 的记忆，注入时必须带「未解决」标记（断言）
3. 跨簇不串：给 credit 域的问题，不注入 ssrm 的记忆
4. 上下文成本：记忆段 ≤ 200 token（断言）

## 8. 面试一句话

「记忆最容易做成『把所有历史塞向量库』，那样只会把噪声灌进上下文。事故记忆的相似性是同现象，而『同现象』我项目里已经有现成的 30 个簇——用簇当索引，比用 embedding 更准，还能解释为什么召回这一条。」
